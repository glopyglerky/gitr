# Rust Git and binary asset upstream research

Inspected 2026-11-08. This is evidence and a proposed reuse policy, not a claim that gitr implements these capabilities. Exact observed upstream heads are in `upstream-snapshot.json`. Selected critical source files were reread at those commit IDs and their blob hashes matched the initial reads.

## Recommended direction

Use gitoxide/gix as the native Git engine. Keep ordinary Git objects, references, packs, repository layouts and Git LFS pointer semantics interoperable with GitHub. Build workflow improvements and a binary asset service above that engine. Borrow Lore's storage architecture where useful; replacing Git's object and transport formats with Lore's formats would lose direct GitHub interoperability.

The first useful native implementation can inspect repository state, identify asset mistakes, generate safe engine-specific attributes, and calculate verified LFS pointers while streaming files. Full clone/fetch/push/merge compatibility is a larger program. Unsupported commands should fail clearly. A compatibility bridge that invokes stock Git is acceptable only if explicitly selected and reported as such. It is not evidence of a Rust replacement.

Asset storage has two explicit modes:

1. **GitHub mode.** Standard LFS v1 pointers and standard LFS APIs. A local chunk cache may deduplicate local storage, but GitHub still receives each full LFS object unless the server itself negotiates another transfer protocol.
2. **Extended asset mode.** The same standard pointers in Git history, plus an explicitly configured Rust asset server/custom transfer adapter for chunk deduplication, shared LAN caches, resumable transfers, stronger lock policy, and large files beyond GitHub's hosted limits. Ordinary Git clients need the matching LFS transfer adapter or a server endpoint that reconstructs full LFS objects.

Do not silently change `.lfsconfig`, credentials, endpoints, sparse selections, history, or tracked asset bytes as a side effect of diagnostics.

## Lore findings that affect the architecture

Lore is real, public, Rust and MIT licensed. The inspected workspace reports version `0.13.1-nightly`. Its core storage and version control layers are separate, so the storage subsystem can be evaluated without adopting Lore history as gitr history. [Workspace](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/Cargo.toml), [system design](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/docs/explanation/system-design.md).

The design uses BLAKE3 for fragment identity, content-defined FastCDC or fixed-size chunking according to content type, and fragment references indexed by byte offset. The canonical FastCDC target is 64 KiB average, 32 KiB minimum and 256 KiB maximum. Larger lists fragment recursively so metadata does not scale as one giant in-memory list. Compression is per fragment and separate from identity. These are design/code facts, not measurements of gitr's performance.

GitHub LFS requires a whole-file SHA-256 identifier. A gitr chunk cache can use a separate local chunk digest, but it must reconstruct the exact original bytes and verify the whole-file SHA-256 before publishing the LFS object. It must never place a BLAKE3 chunk manifest in Git history and call that a standard LFS pointer.

Lore's current basic locks are advisory. Its current public tooling also cannot communicate with the Lore build shipped in UEFN, because that build uses a proprietary compression format. The desktop client currently includes proprietary components and is not yet open source. These caveats rule out claiming that integrating public Lore immediately supplies production UEFN parity or enforced asset locking. [FAQ](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/docs/faq.md), [README](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/README.md).

Lore's current `lore-storage` depends on `zstd-sys`. An all-Rust gitr dependency policy must either omit compression initially, use a verified Rust encoder later, or explicitly isolate that native dependency. A Rust top-level repository does not mean every linked library is Rust. [Manifest](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/lore-storage/Cargo.toml).

## GitHub compatibility boundaries

- Preserve exact Git object bytes and Git's configured object hash; do not substitute BLAKE3 for Git commit IDs. GitHub support and repository object-format support must be tested independently.
- Standard LFS pointers contain the spec URL, a lowercase whole-file `sha256` OID and decimal byte size. The complete pointer is less than 1024 bytes and ends in LF. A parser must not guess that an arbitrary text file is a valid pointer. [LFS spec](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md).
- LFS Batch responses negotiate a transfer agent. Chunk uploads require server support; a fast client cannot add server features by itself. [Xet adapter](https://github.com/huggingface/xet-core/blob/5385084c6e15f0cedd2ca8a2e36279413b049e0c/git_xet/README.md), [Batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md).
- The LFS locking API describes exclusive ownership, verification before push and a single-branch model. Its `ref` currently supplies authentication context, not general branch-scoped locking semantics. Do not claim cross-branch locks from a `ref` field alone. [Locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).
- Current GitHub hosted LFS per-file limits are 2 GB on Free/Pro, 4 GB on Team and 5 GB on Enterprise Cloud. The ordinary Git object hard limit is 100 MB and push limit is 2 GB. A replacement client cannot remove these server limits. [LFS limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage), [repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits).
- Sparse working-copy selection is an I/O optimization, not an access-control boundary. Private asset authorization must apply before digest existence checks and reads. Cross-project dedup can leak equality if the server reveals possession of an unauthorized object. Lore's partition boundary is a useful model here.
- Local undo can restore local state. It cannot erase a public push, revoke someone else's fetched commit, or turn an external side effect into a reversible operation. Record this in the operation journal semantics.

## Problems to solve first

| Developer problem | Implementation direction | Meaningful completion evidence |
|---|---|---|
| Fear of losing work during checkout/rebase/reset | Per-operation snapshots and journal, preview of affected paths, recoverable local worktree/index/ref transactions | Crash injection at every durable boundary; restore tracked, untracked and index states without clobbering newer work; explicit external-effect limits |
| Rebase conflicts and broken stacked branches | Stable change identity, descendant restacking, rerere reuse, clear smartlog | Differential topology/merge tests against Git, recoverable conflicts, no silent history rewrite |
| Large binary revisions duplicate transfers | Streaming LFS filters and verified cache first; optional content-defined chunk service later | Full bytes round-trip, adversarial integrity checks, bounded RSS, measured transfer reduction for insert/edit workloads |
| Artists overwrite non-mergeable assets | Engine-aware attributes, exclusive asset-lock workflow and pre-push verification | Conflict refusal against another writer, lease loss/offline policy, rename/delete paths and multi-branch limitations tested |
| Slow status/checkout in huge trees | Native gix index/status, incremental filesystem notifications, sparse asset views, bounded workers | Cold/warm status on realistic file counts, deleted watch root/overflow recovery, case/Unicode/symlink correctness |
| Tool setup is fragile | One gitr CLI, `doctor`, explicit game profiles, machine-readable errors, standard Git/LFS compatibility output | Clean new clone succeeds on supported platforms and fails with actionable diagnostics when remote capabilities are missing |

For Unreal profiles, preserve `.uasset`/`.umap` binary policy and exclude generated `DerivedDataCache`, `Intermediate`, `Saved` and local build output only when the user chooses the profile. Unity text serialization and stable `.meta` files need a different profile. Never auto-ignore source plugins or production assets based only on an extension.

## Performance policy

Do not adopt the aspirational `gix-lfs` paragraph's old "40x slower" or "Git LFS does not use filter-process" claims. Current Git LFS uses filter-process and upstream 3.8.0, dated 2026-08-27, adds zstd download support. [Current changelog](https://github.com/git-lfs/git-lfs/blob/main/CHANGELOG.md). Benchmark against current Git and current Go Git LFS, not an old straw baseline.

Measure wall time, p50/p95 latency, peak RSS, bytes read, bytes written and network bytes. Distinguish clean clone, warm clone/cache, status, branch switch, sparse hydration, many small assets, a changed multi-GB asset, and compressed versus uncompressed content. Include realistic edit locations and insertions because fixed chunking and content-defined chunking behave differently. Limit outstanding requests and memory. Report hash verification and compression CPU costs, cache eviction and SSD writes. No speedup claim should appear until an identical workload and cache state are measured on both implementations.

## License boundary

The original Git tree is GPLv2-only unless a file states otherwise. Its `COPYING` explicitly says version 2, not a later GPL. Preserve all upstream licenses and notices. Choose gix's MIT alternative when useful. Lore and rustutils/git-lfs are MIT. Apache-2.0-only donors such as jj or Xet require a deliberate license review before incorporation into a GPLv2-only derivative; reading their design does not create that dependency. A separate Rust implementation and an inherited Git source archive must identify their own scope and licenses accurately. Current GitButler FSL restrictions cannot be relabeled away. [Git COPYING](https://github.com/git/git/blob/master/COPYING), [GitButler license](https://github.com/gitbutlerapp/gitbutler/blob/7a2a61bee677aca153064d18b639181ca196c1c5/LICENSE.md).
