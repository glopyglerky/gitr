# Gitr repository database and retrieval choices

Research date: 2026-11-08. These are design recommendations grounded in current upstream sources, not claims that gitr already implements the proposed features. See `upstreams.md` for Git, Git LFS, Lore, and licensing boundaries.

## Recommendation

Use **redb 4.5.0** for the first local transactional catalog, with **`ConcurrencyMode::MultiWriter`**. Preserve ordinary Git objects, hashes, refs, history and transport as the compatibility contract. Store rebuildable commit/tree/file/blob relations and per-blob lexical vectors in the catalog. Automatic hashed lexical vectors can work offline without a model; label them lexical feature vectors, not learned semantic embeddings. Put extraction/model versions in the stored identity so later model upgrades cannot silently mix incompatible vectors.

The reviewed redb head was `ae5bc59145de5a4d9c23079f5b4e244dc9cc0ab7` (2026-11-08). Its manifest is version 4.5.0, Rust 1.90, edition 2024, MIT OR Apache-2.0. The 4.5.0 release changelog dates it 2026-11-05. The public API now supports several processes holding writable database handles, but **only one write transaction is active at a time**. `begin_write()` waits; `try_begin_write()` returns `TransactionError::WouldBlock`. Readers use MVCC snapshots. This improves CLI concurrency and is not distributed high availability.

Sources: [redb manifest](https://github.com/cberner/redb/blob/ae5bc59145de5a4d9c23079f5b4e244dc9cc0ab7/Cargo.toml), [builder and concurrency implementation](https://github.com/cberner/redb/blob/ae5bc59145de5a4d9c23079f5b4e244dc9cc0ab7/src/db.rs), [storage design](https://github.com/cberner/redb/blob/ae5bc59145de5a4d9c23079f5b4e244dc9cc0ab7/docs/design.md), [4.5.0 changelog](https://docs.rs/crate/redb/4.5.0/source/CHANGELOG.md).

### Exact starting API and operational contract

```rust
let database = redb::Database::builder()
    .set_concurrency_mode(redb::ConcurrencyMode::MultiWriter)
    .set_cache_size(16 * 1024 * 1024)
    .create(path)?;
```

Every handle opening the same file must use the same concurrency mode. Multi-process modes require supported byte-range locking on Linux, Apple platforms, or Windows; unsupported platforms must report the error rather than claim shared access. The 4.5.0 protocol is **not compatible with the experimental multi-process protocols in 4.3/4.4**, and incompatibility is not automatically detected. Pin the runtime version used by cooperating processes. Do not copy a live redb file or put it on arbitrary network storage and call that replication.

Build and commit a complete snapshot under its resolved immutable commit OID. A requested revision is resolved once at the start of indexing; the stored result names that exact commit even if a branch moves meanwhile. Search resolves its requested revision and only opens that exact completed snapshot. Never silently search whichever snapshot happened to be indexed last. A failed or interrupted write must expose neither partial path membership nor a completed marker. Old reader transactions remain self-consistent while another process publishes. Store bounded vectors per immutable blob OID and extractor version so unchanged content can be reused across commits.

## Model the repository honestly

A useful first graph is `commit -> root tree`, `tree -> entry`, `entry -> blob/tree/submodule commit`, plus versioned metadata. Those edges are facts encoded in Git. Raw paths are bytes; use an unambiguous byte representation in keys and JSON, so non-UTF-8 paths do not collide through replacement characters. Git symlink payloads are blobs, never permission to follow the working-tree target. Submodule OIDs belong to another object database and must not be loaded as local file blobs.

Token occurrences and lexical similarity are a separate evidence layer. A shared identifier does not prove a call edge. A file-text similarity score does not prove semantic equivalence. Later parser-based symbols and resolved calls require language/toolchain provenance and confidence; embeddings require a model identifier or digest, tokenizer/extractor version, dimension, normalization and distance metric. Search results should show the commit and content identity used, enabling revalidation and reproducibility.

A hashed-token vector should not decide merges, deletions, conflicts or history rewrites. Use it to retrieve candidate files and show exact byte-path/OID provenance. Model execution should be an optional local plugin, not an unrequested network model call or paid hosted dependency. Start with exact cosine over bounded vectors and retain only top-k candidates. Add approximate search when a measured workload demonstrates the need, and expose its recall/latency tradeoff.

The DB is a rebuildable accelerator, not a second authoritative object format. Missing promisor blobs in partial clones require explicit missing-content coverage. A binary or oversized blob remains in the snapshot membership but is excluded from lexical indexing with a reason. Git LFS pointers are text pointing at separate large-file storage; do not claim indexing a pointer indexed the asset content.

## What real multi-writer HA would require

For a later server, distinguish many writer clients from independent competing authorities. Each mutable repository namespace needs a consensus order. A small OpenRaft group could serialize expected-old-OID ref transitions and lock leases, while immutable Git objects and asset chunks replicate separately. Uploading blobs may be parallel and deduplicated. A ref update is acknowledged only after the objects it exposes satisfy the chosen durable replication policy and the authoritative metadata transition reaches its required quorum. Old leaders need fencing; expired leases cannot retain write authority. Path locks also need well-defined repository/ref scope and client tokens.

Readers may use a local index only with explicit freshness rules. A derived index can lag history and be rebuilt; a stale index must never authorize a ref write. Server failover must preserve expected-old-OID compare-and-swap and lock ownership. GitHub remains a Git/LFS remote with its own access and consistency rules; it cannot be drafted into a custom metadata quorum by client code. Conflict-aware reconciliation between GitHub and a gitr server is a distinct synchronization design.

Tests for a real service include partitioned leaders, lost quorum, process death after blob persistence but before metadata commit, failed snapshot restore, stale client CAS, concurrent locks and object garbage collection during reader snapshots. Upstream Raft benchmarks use their own storage/network assumptions; measure end-to-end gitr transactions before publishing throughput claims.
