# Rust forge, Git server and Wasm CI donors for gitr

Review date: **2026-11-09**. This is the forge/CI track of the wider gitr upstream survey. The accompanying `forge-ci.json` records **64 candidates**, their inspection depth, exact snapshots where retrieved, license assessment, reusable boundaries, limitations and primary links. `forge-ci-queries.json` records 28 GitHub query pages with returned repository names.

## Findings that change the implementation plan

The most actionable wholesale reuse is **Rbit's standalone workflow crate**, not a full replacement forge. Its pure planning boundary lets gitr acquire a substantial Actions-compatible language and runner contract while retaining the existing redb durable records, fencing and Wasmi workers. **IronForge and its Plombir derivative** are the strongest compact full-forge source families to compare. **Enroute, the Zed Enroute fork, opendata git-server and reason-machines Aspen** provide more relevant concurrent publication and server-protocol material than the similarly named web viewers. **Mega2** contributes storage/artifact/monorepo infrastructure; **Radicle and GitArena's issues crate** contribute collaboration models. These conclusions are based on the source boundaries discussed below; they are engineering judgments, not upstream benchmark validation.

The user's willingness to change gitr's license broadens the candidate set. Apache-only and AGPL projects remain eligible for a lawful composition or relicensing plan. Existing third-party Git code and dependencies retain their own terms; selecting a new license for authored Rust code does not erase them. Custom restrictions, missing grants and future change dates require separate treatment. The inventory therefore ranks product merit independently of the current repository license, and explicitly identifies the few candidates that are not unrestricted open-source donors today.

### Priority map

| Need in gitr | First donors to inspect/import | Concrete boundary | Main condition |
|---|---|---|---|
| Workflow syntax and job planning | Rbit `rbit-workflow` | Whole independent crate plus its conformance fixtures | Map job plans to gitr jobs/receipts; define supported Actions semantics |
| Native Git serving and a full forge model | IronForge, Plombir | `rg-git` protocol code, HTTP/SSH routes, core/MCP models | Replace unconditional ref publication; select compatible license scope |
| Distributed ref publication and cold objects | Enroute | ledger/compute contract, immutable snapshots, resumable access state machines | Keep one authoritative gitr transaction boundary |
| Real fork improvement | zed-industries/enroute | `wait-for-done` capability fix and regression test | Rebase the isolated patch; do not adopt older fork wholesale |
| Trait-based object-store Git serving | opendata git-server; Aspen | protocol adapters, pack/ref validation contracts, interop fixtures | Adapt backends to redb; pre-alpha maturity in Aspen |
| Issues/patches and signed collaboration | GitArena `gitarena-issues`; Radicle | issue operation codec, snapshots, signed collaborative objects | Reconcile with gitr atomic refs and SQL-free authority |
| Artifacts, LFS, OCI, agent traces | Mega2 | focused storage/ingest/API models | PostgreSQL/native dependency coupling in the full product |
| DAG/matrix and execution policy | Oxide CI; FluentCI | graph/matrix functions and task-policy types | No assumption these supply durable Wasmi scheduling |
| Durable replay and receipts | Obelisk; Homestar | storage/replay contracts, content-addressed receipt schemas | Wasmtime and DB/runtime coupling; preserve Wasmi |
| MCP surface | forgejo-mcp-rs; IronForge | tool schemas/DTOs and auth scope patterns | Client adapter is not already a stateless authenticated gitr API |

## 1. Rbit: the best contained CI import

[GitRbit/rbit](https://github.com/GitRbit/rbit) is dual **MIT OR Apache-2.0**, even though GitHub's repository-level detector reports Apache. The workspace has both license files. Its `crates/rbit-workflow` explicitly isolates decisions that depend only on the workflow document and input event. It has no I/O, async or dependency on other Rbit crates. The inspected manifest lists a small set of parsing/serialization/regex/secret-handling dependencies. This makes a whole-crate import plausible rather than merely a collection of implementation ideas. Sources: [workspace manifest](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/Cargo.toml), [MIT grant](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/LICENSE-MIT), [crate manifest](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-workflow/Cargo.toml), [public module boundary](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-workflow/src/lib.rs).

The useful surface includes budgeted YAML parsing and structured errors; branch/tag/path filter semantics; push, PR, dispatch and scheduled triggers; expression evaluation; cron calculation; matrix expansion; reusable-workflow planning; built-in action resolution; concurrency groups; stored job templates; runner job specifications; protocol version/body limits/error types; and redacting, zeroizing secret values. These are exactly the pieces gitr lacks above its durable job primitive. The source tree also contains workflow conformance fixtures, useful for agreeing on what compatibility means. Source: [module map](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-workflow/src/lib.rs) and [conformance fixtures](https://github.com/GitRbit/rbit/tree/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-workflow/tests/conformance).

The integration should compile a workflow/event into immutable plans, then create gitr jobs and inputs in redb. Worker lease/fence checks, task ownership, result receipts, retry publication and atomic completion should remain gitr responsibilities. Built-in actions that launch processes, access secrets or fetch remote material need explicit host capabilities; parsing an Actions file does not make every action safe or available under Wasmi. The full Rbit product uses SQLite, and its Git transport invokes system Git. Its broader scheduler and transport are useful comparison material, but should not be mistaken for a fully native engine suitable for wholesale replacement. Sources: [scheduler](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-services/src/actions/scheduler.rs), [receive transport](https://github.com/GitRbit/rbit/blob/39f932a00b7aa35b324e06a9ff2343a57d4bed76/crates/rbit-transport/src/receive.rs).

## 2. IronForge and Plombir: broad product functionality, with a publication correction

[lengyuqu/ironforge](https://github.com/lengyuqu/ironforge) is a substantial current Rust forge with an actual **MIT** license file. Its modular workspace exposes `rg-git`, `rg-http`, `rg-ssh`, `rg-core`, `rg-mcp`, `rg-ci`, `rg-runner` and `rg-ci-isolation`. The Git module implements upload/receive protocol behavior over gix rather than making every Git operation a system-Git subprocess. This is useful native serving code, while the forge, SQL persistence and frontend build are a larger integration undertaking. Sources: [license](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/LICENSE), [workspace](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/Cargo.toml), [Git entry points](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/crates/rg-git/src/lib.rs), [upload-pack](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/crates/rg-git/src/protocol/upload_pack.rs), [MCP entry points](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/crates/rg-mcp/src/lib.rs).

**Do not transplant its ref commit path unchanged.** In the inspected receive-pack implementation, ref updates are sequential, atomic capability is deliberately absent, and `update_ref` takes the ref name/new object ID but uses gix `PreviousValue::Any`. That function does not carry the client's expected old object ID into the actual reference write. Even if earlier validation checks refs, it is not the same as an atomic comparison at publication. This is a concrete boundary where gitr's existing fencing and CAS work should replace donor behavior. The packet framing, status handling and command parsing can still be valuable. Source: [receive-pack implementation](https://github.com/lengyuqu/ironforge/blob/56893d83fc6d39551623ace292cad725c8b6fdd5/crates/rg-git/src/protocol/receive_pack.rs).

[Nettechnologys/plombir-git](https://github.com/Nettechnologys/plombir-git) is a documented derivative of IronForge, previously called ForgeKeep. It carries **AGPL-3.0-or-later** for its work, with a NOTICE preserving IronForge's MIT terms and explaining the upstream license-file history. This is verified derivative lineage even if a repository is detached from a GitHub fork network. Its workspace includes a related `rg-git`, richer mirror scheduling, CI matrix support, HTTP/SSH/MCP, package registry and process handling. Sources: [lineage and upstream notice](https://github.com/Nettechnologys/plombir-git/blob/0342827a064022fb10a5652f822d0a3c7bd5602e/NOTICE), [license](https://github.com/Nettechnologys/plombir-git/blob/0342827a064022fb10a5652f822d0a3c7bd5602e/LICENSE), [workspace](https://github.com/Nettechnologys/plombir-git/blob/0342827a064022fb10a5652f822d0a3c7bd5602e/Cargo.toml), [architecture](https://github.com/Nettechnologys/plombir-git/blob/0342827a064022fb10a5652f822d0a3c7bd5602e/docs/how-it-is-built.md).

Compare the two on code behavior and desired product breadth, not just license labels. If Plombir has a clearly superior module, the user's revised licensing preference allows it to be considered. Preserve upstream MIT notices and account for the derivative's AGPL obligations where that code is integrated. Do not assume that an ancestor's permissive license licenses later fork changes permissively. The full fork's receive-path correctness was not exhaustively audited in this pass.

## 3. Git servers with meaningful storage and concurrency design

### Enroute and the useful Zed fork

[enroute-sh/enroute](https://github.com/enroute-sh/enroute) is **Apache-2.0**. It separates compute from storage, gives repositories replicated ledger histories and uses optimistic reference publication and immutable snapshots. Its source offers a particularly clear reusable pattern for reads over cold object layers: a machine performs locally available work, parks independent items waiting on remote data, and resumes each item when its own dependencies arrive. This may fit gitr's future object-storage tier without making every algorithm fully async or restarting large walks. Sources: [license](https://github.com/enroute-sh/enroute/blob/f2b4e149d73ab2904b2618c697e16abd803ffde0/LICENSE), [architecture overview](https://github.com/enroute-sh/enroute/blob/f2b4e149d73ab2904b2618c697e16abd803ffde0/README.md), [resumable object work](https://github.com/enroute-sh/enroute/blob/f2b4e149d73ab2904b2618c697e16abd803ffde0/crates/compute/src/repo/machine.rs).

The full product chooses its own ledger/log and layer-storage stack, with raft-related, LSM, native allocator and crypto dependencies visible in manifests. It is a serious alternative design to study, not a reason to silently replace redb. Claims about performance, model checking and Jepsen are upstream claims; this research inspected sources and did not rerun those suites. Sources: [manifest](https://github.com/enroute-sh/enroute/blob/f2b4e149d73ab2904b2618c697e16abd803ffde0/Cargo.toml), [project claims](https://github.com/enroute-sh/enroute/blob/f2b4e149d73ab2904b2618c697e16abd803ffde0/README.md).

The fork sweep produced an actual useful difference: **[zed-industries/enroute](https://github.com/zed-industries/enroute)**, whose GitHub parent is Enroute, is one unique commit ahead and one commit behind the compared upstream snapshot. Commit [d29138ad3a8806effc7bbe72ddf6a1ad214401cc](https://github.com/zed-industries/enroute/commit/d29138ad3a8806effc7bbe72ddf6a1ad214401cc) advertises `wait-for-done` and adds an interoperability regression for `push.negotiate`. The test arranges history not reachable from advertised tips and checks the resulting push pack and repository. This is a compact fix/test worth carrying wholesale into any compatible native protocol server. [Pinned comparison](https://github.com/enroute-sh/enroute/compare/f2b4e149d73ab2904b2618c697e16abd803ffde0...zed-industries:d29138ad3a8806effc7bbe72ddf6a1ad214401cc).

### opendata git-server

[opendata-oss/git-server](https://github.com/opendata-oss/git-server) is **MIT** and directly targets native Git serving over an object-backed database. The inspected receive-pack source has a useful split among command framing, validation/promotion and CAS result/status reporting. Its main value is the protocol/storage boundary and associated invariants. It uses gix with SlateDB/object storage, while authentication, PRs and branch-protection product features are explicitly beyond its scope. Reuse the server semantics with a gitr storage adapter rather than adopting its whole persistence stack merely to obtain Git-over-HTTP. Sources: [scope](https://github.com/opendata-oss/git-server/blob/34ff6ac6804ea17759b2f5673abab6c23b9667d4/README.md), [dependencies](https://github.com/opendata-oss/git-server/blob/34ff6ac6804ea17759b2f5673abab6c23b9667d4/Cargo.toml), [receive protocol](https://github.com/opendata-oss/git-server/blob/34ff6ac6804ea17759b2f5673abab6c23b9667d4/src/protocol/receive_pack.rs), [license](https://github.com/opendata-oss/git-server/blob/34ff6ac6804ea17759b2f5673abab6c23b9667d4/LICENSE).

### Aspen, with a name collision worth avoiding

[reason-machines/aspen](https://github.com/reason-machines/aspen) is **Apache-2.0** and is distinct from the Iroh/redb-oriented `brittonr/aspen` covered by the storage track. It has dedicated protocol, pack, planner, metadata and authentication crates. Its metadata contract models versioned refs, expected versions for CAS, pack closures/dependencies, commit-index lookup that distinguishes unknown from absent, and jobs enqueued with publication. Those interfaces and its interop/fuzz/chaos fixtures are strong material for gitr's correctness work. Sources: [metadata contract](https://github.com/reason-machines/aspen/blob/9499174b57c236bcee0778c946cc4249c5ec2602/crates/aspen-core/src/meta.rs), [crate boundaries](https://github.com/reason-machines/aspen/blob/9499174b57c236bcee0778c946cc4249c5ec2602/Cargo.toml), [status and architecture](https://github.com/reason-machines/aspen/blob/9499174b57c236bcee0778c946cc4249c5ec2602/README.md).

The project explicitly identifies itself as pre-alpha and records unmet launch gates; do not market it as production-proven. PostgreSQL and SQLite implementations do not remove the value of its core types but do prevent calling the complete system a redb replacement with no migration cost. The inspected fork `whatif-dev/git-oss-aspen` had no unique commit and was three behind, so it supplied no demonstrated donor advantage over the origin at these snapshots.

### Walgit and detached derivatives

[tobi/walgit](https://github.com/tobi/walgit) is the **MIT** origin of a useful family of stateless Git/object-store designs using a manifest and write-ahead history around object-store CAS. [burrr-ai/gitcask](https://github.com/burrr-ai/gitcask) explicitly describes itself as a fork of Walgit; its current work is **Apache-2.0**, oriented toward a platform managing many small repositories. [gqf2008/walgit-d1](https://github.com/gqf2008/walgit-d1) documents another Walgit derivative, adding signed collaboration/CI protocol objects and a Rust aggregation path. Sources: [Walgit design](https://github.com/tobi/walgit/blob/80e9a20b29e29aefd16a4dae6f8e274cce85cca5/README.md), [Gitcask lineage](https://github.com/burrr-ai/gitcask/blob/60860713e0848f9da2a9aeb942a59a5db0e09d2b/README.md), [Gitcask license](https://github.com/burrr-ai/gitcask/blob/60860713e0848f9da2a9aeb942a59a5db0e09d2b/LICENSE), [D1 protocol](https://github.com/gqf2008/walgit-d1/blob/3fb496e5cd3e4e492b6457ad7fb451e60b4e117b/docs/D1_PROTOCOL.md), [D1 aggregation](https://github.com/gqf2008/walgit-d1/blob/3fb496e5cd3e4e492b6457ad7fb451e60b4e117b/crates/walgit-wal/src/collab.rs).

They are worth comparing for immutable-object publication, manifests and collaboration events. D1 is not entirely Rust: the `wg` client and its MCP support use Zig, and a TypeScript SDK is also present. Each family's authority/consistency model must be translated into gitr's fenced redb model, not layered as a second competing mutable truth.

A same-name detached copy, `Bzhs5820/walgit`, altered its README toward an unusually placed ZIP download (`Software-premold.zip`). No archive was downloaded or executed, and no substantive improvement over the origin was established. It is not recommended as a source; this observation does not establish that the archive is malicious. Source: [copy's README](https://github.com/Bzhs5820/walgit/blob/24279642e264acf26126f1a211fa6a8052084903/README.md).

## 4. Mega2, Radicle and GitArena: broader repository and collaboration data

### Mega2

The old [gitmono-dev/mega](https://github.com/gitmono-dev/mega) is archived. The current [gitmono-dev/mega2](https://github.com/gitmono-dev/mega2) root manifest and MIT file establish **MIT OR Apache-2.0**, despite GitHub's Apache-only detection. Mega2's public product is storage/trunk oriented, with Git Smart HTTP, read-only SSH and object/artifact services; it should not be described as an already complete multibranch PR/Change List forge UI. Sources: [current scope](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/README.md), [dual-license and dependencies](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/Cargo.toml), [MIT grant](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/LICENSE-MIT).

Ceres pack ingestion and publication, Jupiter storage types, LFS/OCI/artifact handling, and agent-capture/audit models are the most useful donor areas. The source tree retains substantial APIs and storage models beyond the public product's central path, so do not infer supported end-to-end behavior from filenames. Whole-system reuse brings PostgreSQL and native components: the manifest explicitly includes OpenSSL and a libvault OpenSSL adaptor, among other platform dependencies. Sources: [push chain](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/src/ceres/pack/push_chain.rs), [artifact storage](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/src/jupiter/storage/artifact_storage.rs), [OCI storage](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/src/jupiter/storage/oci_db_storage.rs), [dependencies](https://github.com/gitmono-dev/mega2/blob/c75c6d68132e289456fe16e28c38b868fc780f63/Cargo.toml).

### GitArena's issues crate

[mellowagain/gitarena](https://github.com/mellowagain/gitarena) is **MIT**, and its contained `gitarena-issues` is a promising issue-operation library built around git-bug data. It exposes issue creation, comments, status, snapshots and merge operations; its own integration suite targets git-bug 0.11.0. This is more direct reuse for a Git-backed collaboration model than importing a whole forge. Sources: [issue API and limitations](https://github.com/mellowagain/gitarena/blob/cddcdab38d89f036d9eccb7a15021707c84282cd/gitarena-issues/README.md), [manifest](https://github.com/mellowagain/gitarena/blob/cddcdab38d89f036d9eccb7a15021707c84282cd/gitarena-issues/Cargo.toml), [license](https://github.com/mellowagain/gitarena/blob/cddcdab38d89f036d9eccb7a15021707c84282cd/gitarena-issues/LICENSE.txt).

The same README candidly documents two serious boundaries: ref updates can lose external `git`/`git-bug` writes because the old value is checked before taking the ref lock; and Git writes do not share a transaction with caller SQL writes. gitr should reuse operation encoding and snapshots while routing commit/ref publication through its own atomic authority. The full forge includes gix, **libgit2 via git2**, PostgreSQL and web UI code, so it is not all pure-Rust persistence. Source: [full forge dependencies](https://github.com/mellowagain/gitarena/blob/cddcdab38d89f036d9eccb7a15021707c84282cd/gitarena/Cargo.toml).

### Radicle and decentralized alternatives

[radicle-dev/heartwood](https://github.com/radicle-dev/heartwood) has a dual **MIT OR Apache-2.0** workspace. The most valuable areas are collaborative objects for issues/patches, identity and signatures, DAG support and ref-name validation. Source boundaries include `radicle-cob`, `radicle-crypto`, `radicle-dag` and `radicle-git-ref-format`. The manifest also exposes vendored libgit2 and SQLite, which must be accounted for in any “Rust-only” profile. Signed and mergeable collaboration is complementary to, rather than a proof of, linearizable mutable-ref publication. Source: [workspace/dependencies](https://github.com/radicle-dev/heartwood/blob/8b053320dc3d5dc2189be3105546ed4d852b0583/Cargo.toml) and [crates](https://github.com/radicle-dev/heartwood/tree/8b053320dc3d5dc2189be3105546ed4d852b0583/crates).

[freenet/freenet-git](https://github.com/freenet/freenet-git) offers LGPL3 repository/pack contracts and a remote helper over Freenet. [Twigpine/node](https://github.com/Twigpine/node) is a different, GitLawb-named libp2p/Ed25519 identity/attestation family; its manifest and files are dual MIT/Apache despite GitHub's NOASSERTION classification. They expand the decentralized comparison set, but neither is an Iroh transport library or drop-in substitute for gitr's authority. Sources: [Freenet workspace](https://github.com/freenet/freenet-git/blob/668d069982aa298eba256aa6977c75f377b3d7c8/Cargo.toml), [GitLawb workspace](https://github.com/Twigpine/node/blob/c805e35f40873a120c81bf00d9ddb50da956fd97/Cargo.toml).

## 5. Wasm CI and durable workflow donors

Keep **Wasmi** as the selected runtime. The inspected upstream manifest remains dual MIT/Apache. The existence of Wasmtime or Extism inside an attractive project is evidence about its adaptation cost, not a requirement to change gitr's runtime. Source: [Wasmi workspace](https://github.com/wasmi-labs/wasmi/blob/a9e9b0b01c9e23e4f7e1706543a7f73020cc57ef/Cargo.toml).

**Oxide CI** is MIT and contains directly useful DAG validation, matrix expansion and workflow-spec code, plus an Extism plugin host. The actual scheduler stores active runs and pending execution state in in-memory lock-protected collections. That rules out presenting it as a ready replacement for gitr's persistent scheduler, irrespective of PostgreSQL/NATS elsewhere in the product. Start with its pure graph/matrix modules if Rbit does not cover a desired policy. Sources: [DAG module](https://github.com/copyleftdev/oxide-ci/blob/8aabcce9837cfb6c3966c613abc6384a23210d92/crates/oxide-scheduler/src/dag.rs), [matrix module](https://github.com/copyleftdev/oxide-ci/blob/8aabcce9837cfb6c3966c613abc6384a23210d92/crates/oxide-scheduler/src/matrix.rs), [scheduler state](https://github.com/copyleftdev/oxide-ci/blob/8aabcce9837cfb6c3966c613abc6384a23210d92/crates/oxide-scheduler/src/scheduler.rs), [plugin host dependencies](https://github.com/copyleftdev/oxide-ci/blob/8aabcce9837cfb6c3966c613abc6384a23210d92/crates/oxide-plugins/Cargo.toml).

**FluentCI engine** is MPL2 and offers richer retry, conditional task execution, output/artifact and host-tool orchestration policies. Its Wasm extensions call into a host that can execute Nix/pkgx and other processes. “Wasm plugin” therefore describes the extension mechanism, not an automatic sandbox for every command it starts. Its task policies may be useful independently of its full host stack. Sources: [execution model](https://github.com/fluentci-io/fluentci-engine/blob/9c87f4a74606dc199dd9bbcbb7a62b3d76d18bca/README.md), [workflow implementation](https://github.com/fluentci-io/fluentci-engine/blob/9c87f4a74606dc199dd9bbcbb7a62b3d76d18bca/crates/executor/src/workflow.rs), [license](https://github.com/fluentci-io/fluentci-engine/blob/9c87f4a74606dc199dd9bbcbb7a62b3d76d18bca/LICENSE).

**Obelisk** is an AGPL durable Wasm execution engine with explicit execution-log, version, retry and storage contracts. It is strong material for studying replay, crash recovery and execution ownership. Its selected runtime is Wasmtime and its database profiles are SQLite/PostgreSQL; the project is still pre-release. Adapt a proven contract or test, rather than inserting its runtime/storage authority into gitr unchanged. Source: [storage/replay contract](https://github.com/obeli-sk/obelisk/blob/f7c06e41b05b389de7df2921294482f62b958970/crates/concepts/src/storage.rs), [manifest](https://github.com/obeli-sk/obelisk/blob/f7c06e41b05b389de7df2921294482f62b958970/Cargo.toml).

**Homestar** is Apache2 and separates content-addressed invocation, workflow and receipt concerns. Those schemas align with gitr's durable receipt work. It has a much older activity snapshot (last observed push 2024-09-26), and a Wasmtime/SQLite/libp2p stack. Treat it as schema/design material until dependency freshness is reviewed. Sources: [manifest](https://github.com/ipvm-wg/homestar/blob/0f0a4f5b4c00c856c6eb865da087c0332b119e8d/Cargo.toml), [workflow boundary](https://github.com/ipvm-wg/homestar/blob/0f0a4f5b4c00c856c6eb865da087c0332b119e8d/homestar-workflow/src/lib.rs).

**ci-with-wasm** combines Extism, gix shallow cloning and rootless Youki containers, but no license grant was found in its manifest, README or inspected tree. It remains a discovery lead, not a copying recommendation. Cicada is archived and centered on TypeScript/Deno pipelines; Toast and Pipelight are useful Rust host/container pipeline comparisons but not native Wasmi durable schedulers. Dagrs, Maelstrom and Moon are recorded as secondary DAG/runner candidates, with metadata-level rather than deep source review. Sources and exact inspection levels are in the JSON inventory.

### CI outside GitHub

[Radicle CI](https://radicle-ci.liw.fi/) is especially relevant because its [broker architecture](https://radicle-ci-broker.liw.fi/architecture.html) turns repository events into persistent jobs and invokes adapters through a small JSON interface. The [current crate documentation](https://docs.rs/radicle-ci-broker/latest/radicle_ci_broker/) and [adapter documentation](https://docs.rs/radicle-ci-adapter/latest/radicle_ci_adapter/) provide useful event/runner boundaries and collaborative-object receipts. This could inform gitr's event-to-CI handoff even when its worker runs Wasmi.

The canonical Radicle-hosted source view hit a redirect loop. An older broker version's docs declare dual MIT/Apache, but this pass did not pin and license-audit the current 0.32.1 source. The GitHub `gsaslis/radicle-ci-broker` mirror is old. Do not silently equate that mirror with the current project.

[Ambient](https://ambient.liw.fi/) is another related official source: AGPL3-or-later, VM-isolated and designed for offline execution. Its site describes it as beta used in production. This is an isolation design reference, not evidence that a Wasm worker already has VM-equivalent host containment.

Ahead/behind numbers describe the compared snapshots and will change. The JSON retains origin/fork metadata, pinned heads where inspected and the useful Enroute comparison. Project names alone do not establish a fork, rewrite or derivative.

GitHub repository queries included `fork:true`, broad forge/hosting/server searches, and targeted Rbit/IronForge/Mega2/Enroute/Aspen/GitArena/Walgit/FluentCI families. The broader forge query was paginated through its final two-result page. Rust-filtered Walgit returned 190 results across two populated pages plus a checked empty page. Narrower name-family queries were completed where below the page limit. Broad hosting was bounded at four 100-result pages; broad server/CI searches were bounded at one page. Those broad sets contain many irrelevant forks and are not presented as a complete global census.

The connector rejected direct GitHub `/forks` list requests, so the fallback was repository search plus parent/source metadata and selected compare requests. Official docs/crates and web discovery expanded the search to Codeberg, GitLab and Radicle; Codeberg/sourcehut crawling restrictions and the Radicle redirect prevented some direct source audits. The Codeberg Forgejo MCP mirror was available on GitHub. A GitLab Rust-gitforge lead is recorded as discovery-only, not counted as source audited.

No upstream repository was built, executed or benchmarked in this track. The strongest recommendations are based on source inspection, not a claim that every donor passes gitr's invariants. This is an extensive, reproducible public-source search with explicit bounds; it cannot prove that every private, unindexed or inaccessible repository on the internet has been found.

## 9. Recommended import sequence

1. **Pin Rbit's workflow crate and fixtures.** Establish the workflow/event → immutable gitr plan mapping, supported syntax and budget/error behavior. Keep storage, scheduling and Wasmi execution in gitr.
2. **Compare native serving modules from IronForge and opendata.** Keep protocol parsing separated from authorization and final publication. Carry all expected old refs into one gitr fenced transaction; correctly report partial/atomic semantics.
3. **Add the Enroute/Zed negotiation regression.** Exercise protocol v2, hidden history, pack minimization and strict Git integrity checking against gitr's selected serving path.
4. **Use Aspen/Enroute contracts to expand durability testing.** Focus on concurrent writers, stale expectations, crash before/after publication, incomplete indexes, immutable snapshots and cold-object resumption. Do not replace redb speculatively.
5. **Choose a collaboration model.** GitArena git-bug operations are a compact import; Radicle signed collaborative objects offer a broader distributed identity/patch model. Put both behind gitr's durable mutation boundary.
6. **Add forge product/MCP surfaces from a single coherent family.** IronForge/Plombir are the first comparison, with Reef and Forgejo MCP as secondary schema/API donors. Avoid importing several overlapping authentication/permission systems.
7. **Extend CI execution policy only for demonstrated gaps.** Oxide graph/matrix, FluentCI policy, Obelisk replay and Homestar receipts are selectable modules; Wasmi remains the runtime.
8. **Take Mega2 artifact/OCI/trace infrastructure when demanded by product scope.** Keep optional heavy services distinct from the minimal Git/DB/worker profile.

Before a real code import, record exact source commit, copied paths, license/notice files, dependency features, imported tests and the gitr adapter boundary. That produces a reviewable implementation proposal instead of an unmaintainable collection of overlapping upstream systems.
