# Rust Git name-family and small-donor research

Research date: 2026-11-08, America/Denver. Scope: upstream projects with names such as `gitr`, `rgit`, `gitrs`, `rsgit`, `rs-git`, `git-rs`, `git_rs`, `rust-git`, `rustgit`, `rusty-git`, `girt`, and closely related Git, forge, agent, and storage projects.

## Findings that should change implementation choices

The most useful newly identified implementation candidates are **joshka/girt** and **no-std-rs/git-zero**. Both have real object/pack/transport code and permissive license texts. They deserve an integration experiment beside the established Git engine options. Neither supplies gitr's complete durable, concurrent database authority. This research reviewed source and contracts, not runtime correctness or performance.

For an immediate, small transplant, **ferrislabs/gitr's graph crate** is more attractive than adopting an entire similarly named client. Its lane-layout module is separated from the GUI and I/O. **cNameHitch/gitr's interoperability fixtures** and **mayhemheroes/git-rs's fuzz target** are useful ways to increase independent behavioral coverage before importing another engine. [crates/graph/src/lib.rs](https://github.com/ferrislabs/gitr/blob/40f634624b639c27e6bdf99bc2020e1a8d6bafe5/crates/graph/src/lib.rs); [crates/git-cli/tests/common/mod.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-cli/tests/common/mod.rs); [fuzz/Cargo.toml](https://github.com/mayhemheroes/git-rs/blob/12a603036f29d5a73f0fab7f7da60dcdbf74c44b/fuzz/Cargo.toml).

Names are poor indicators of capability. The same `gitr` name describes a native implementation, a Git CLI/MCP wrapper, a gix-backed GUI, a libgit2-backed viewer, and a Git subprocess client. Some convincing descriptions have no corresponding engine. **borislitv/git-rs has only a README**, and **jimmy-lt/gitrs's only library source defines a version constant**. These are excluded as implementation donors. [README.md](https://github.com/borislitv/git-rs/blob/327b16d71c7410e2b69563835a460cde9ea9cb28/README.md); [src/lib.rs](https://github.com/jimmy-lt/gitrs/blob/d7d275c80657805c433e488981e41702a8346cdc/src/lib.rs).

Ranking below follows engineering fit. The license column records the source's actual terms rather than assuming gitr's present authored-code license is permanent. A change to gitr's own license does not create permission for unlicensed third-party code or remove another project's restrictions.

## Priority donors and their actual boundaries

### joshka/girt

The inspected manifest is version 0.18.0. The project has an async `ObjectRead`/`ObjectWrite` boundary, a dynamic-dispatch adapter, memory/filesystem stores, pack codecs, native transfer workflows, and upload/receive service modules. The storage trait accepts a DB or network implementation, verifies object identities, and supports overriding `read_many` for batched retrieval. This is closely aligned with a database-backed gitr object store. [Cargo.toml](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/Cargo.toml); [src/storage.rs](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/src/storage.rs); [src/serve.rs](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/src/serve.rs).

A redb adapter can be evaluated without adopting girt's filesystem as authoritative storage. However, the source explicitly says **reference storage is not yet pluggable** and points to issue 515. Its files-reference transaction documentation allows partial publication, intermediate reader-visible states, and failures between reference and reflog updates. Successful visibility does not promise fsync or crash survival. Those properties cannot be silently promoted to gitr's stronger transactional contract. [src/storage.rs](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/src/storage.rs); [docs/reference-transactions.md](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/docs/reference-transactions.md).

The root manifest includes `aws-lc-rs` and optional Rustls with the AWS-LC provider. Thus a Rust implementation of Git here does not establish an entirely Rust dependency closure. The source is dual MIT/Apache-2.0. Treat the API as experimental and pin its revision before any adoption. [Cargo.toml](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/Cargo.toml); [LICENSE-MIT](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/LICENSE-MIT); [LICENSE-APACHE](https://github.com/joshka/girt/blob/5558e436cd050a33034f55e88c5d923aa0046fd2/LICENSE-APACHE).

Recommended experiment: implement read-only object access through gitr's DB, run the same object/pack cases through gix, girt and C Git, and only then evaluate a write path. Keep ref authorization, CAS expectations, durable commit and recovery in gitr.

### no-std-rs/git-zero

The actual core crate has `#![no_std]` and `#![forbid(unsafe_code)]`, with SHA-1, collision-checked SHA-1 and SHA-256 dependencies configured without defaults. The repository contains separate core, client, server, and native adapter crates. The host owns buffers, I/O, repository enumeration and persistence. This makes the protocol/codec crates plausible whole-crate imports for a database-backed host. [crates/git-zero-core/src/lib.rs](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/crates/git-zero-core/src/lib.rs); [crates/git-zero-core/Cargo.toml](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/crates/git-zero-core/Cargo.toml); [Cargo.toml](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/Cargo.toml).

Its `Repository` contract requires stable objects and exact identities throughout a request and across discovery/fetch for the same repository URL. A streaming `read_object(index, offset, storage)` path lets the caller avoid holding each full object in memory. A gitr adapter must pin the corresponding DB snapshot and keep it valid through the response. [crates/git-zero-core/src/repository.rs](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/crates/git-zero-core/src/repository.rs).

Receive-pack parsing is usefully separated from authority. The receive module explicitly leaves authentication, quarantine, delta resolution, graph/ref validation and publication to the host, and does not acknowledge pushes itself. A gitr implementation can place its durable transaction before the report-status acknowledgement. The code only permits advertised capabilities that the host opts into. [crates/git-zero-server/src/receive/mod.rs](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/crates/git-zero-server/src/receive/mod.rs).

Allocation-free does **not** mean constant-memory at repository scale. `SelectionStorage` requires object metadata and index arrays sized to the complete repository object count, while revision filtering adds one state byte per object. Large-repository tests must include that memory, not merely packet buffers. The README also says Linux-scale hosting remains unverified. [crates/git-zero-server/src/upload_pack/storage.rs](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/crates/git-zero-server/src/upload_pack/storage.rs); [README.md](https://github.com/no-std-rs/git-zero/blob/9efd2f70da9247411feb6bd79d4b291cd618c6b6/README.md).

Recommended experiment: embed its wire decoder and pack verifier first. Evaluate the complete server path only after proving bounded behavior with large histories, malicious packs, cancellation, snapshot retention and restart during publication.

### cNameHitch/gitr and arbruijn/gitr

This is a real 16-member workspace, not just a similarly named README. It separates hashes, objects, loose/pack storage, refs, indexes, diffs, merges, revision walking, transport, protocol, and CLI code. It includes an `OdbBackend` interface. The concrete `ObjectDatabase` still owns loose/pack filesystem stores and writes to loose storage, so the trait does not make it a drop-in redb engine. [Cargo.toml](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/Cargo.toml); [crates/git-odb/src/backend.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-odb/src/backend.rs); [crates/git-odb/src/lib.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-odb/src/lib.rs).

The README's completeness claim needs stronger proof than this source pass provides. Local transport runs `git-upload-pack` or `git-receive-pack`; SSH invokes an external process. The SSH shell-string path needs an input/escaping review before reuse. One clone interoperability test checks working-tree files only if a particular output file exists, so a passing test can omit the intended checkout assertion. [crates/git-transport/src/local.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-transport/src/local.rs); [crates/git-transport/src/ssh.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-transport/src/ssh.rs); [crates/git-cli/tests/e2e_remote_tests.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-cli/tests/e2e_remote_tests.rs).

The most attractive immediate material is its deterministic test setup and behavioral fixture coverage. Adapt the strict full-parity assertions and strengthen conditional/ignored assertions. The MIT license permits evaluation and reuse with its conditions; runtime compatibility remains unproven here. Both upstream and arbruijn's default head resolve to `e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d`, so this fork currently contributes no separate default-branch code. [crates/git-cli/tests/common/mod.rs](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/crates/git-cli/tests/common/mod.rs); [LICENSE](https://github.com/cNameHitch/gitr/blob/e7a45704365bcbd4f9f6a5d83c4df07efcd5c59d/LICENSE); [upstream head](https://api.github.com/repos/cNameHitch/gitr/git/ref/heads/main); [fork head](https://api.github.com/repos/arbruijn/gitr/git/ref/heads/main).

### ferrislabs/gitr

The `gitr-graph` crate is the cleanest small import in this name family. Its public module says the layout depends only on the input commit sequence, with no GUI, I/O or clock. It expects commits in topological order, so gitr must retain that precondition. The repository also contains dedicated layout tests. The application uses gix and GPUI, but importing the graph crate and necessary domain types does not require adopting that GUI. [crates/graph/src/lib.rs](https://github.com/ferrislabs/gitr/blob/40f634624b639c27e6bdf99bc2020e1a8d6bafe5/crates/graph/src/lib.rs); [crates/graph/src/layout.rs](https://github.com/ferrislabs/gitr/blob/40f634624b639c27e6bdf99bc2020e1a8d6bafe5/crates/graph/src/layout.rs); [Cargo.toml](https://github.com/ferrislabs/gitr/blob/40f634624b639c27e6bdf99bc2020e1a8d6bafe5/Cargo.toml).

### ekhodzitsky/gitr

This is relevant to the requested MCP/API product even though it is not a native Git implementation. Its workspace separates library, CLI, MCP and Tower integration. It wraps system Git with typed commands, errors and parse fixtures. The standalone MCP binary is a useful API/schema comparator; transplanting it wholesale would preserve subprocess and authorization assumptions that gitr needs to replace. [Cargo.toml](https://github.com/ekhodzitsky/gitr/blob/cb557361d470303374217a41a0cc07f8f52d9cc6/Cargo.toml); [README.md](https://github.com/ekhodzitsky/gitr/blob/cb557361d470303374217a41a0cc07f8f52d9cc6/README.md); [crates/gitr-mcp/src/main.rs](https://github.com/ekhodzitsky/gitr/blob/cb557361d470303374217a41a0cc07f8f52d9cc6/crates/gitr-mcp/src/main.rs).

### Related projects with storage or collaboration code

**neul-labs/grite** has event types, deterministic issue projections, signing and a Git WAL adapter. Its projection choices include last-writer-wins fields, set-like labels/assignees, and append-only comments. These are promising issue-tracker components, but accepting last-writer-wins for issue text is a separate decision from permitting it for repository refs. The core manifest uses sled and tree-sitter; the Git adapter uses git2. Move selected models/projection logic behind gitr's store and Git interface instead of pulling in a second database and native Git binding. [crates/libgrite-core/src/lib.rs](https://github.com/neul-labs/grite/blob/33afee09adda9e7e5be464e846bca800da56212c/crates/libgrite-core/src/lib.rs); [crates/libgrite-core/Cargo.toml](https://github.com/neul-labs/grite/blob/33afee09adda9e7e5be464e846bca800da56212c/crates/libgrite-core/Cargo.toml); [crates/libgrite-git/Cargo.toml](https://github.com/neul-labs/grite/blob/33afee09adda9e7e5be464e846bca800da56212c/crates/libgrite-git/Cargo.toml).

**Uranid/mnem** has redb blockstore and operation-head code, ANN modules and retrieval infrastructure. The operation-head update uses one redb write transaction to add a new head and remove supplied superseded heads. Its tests intentionally retain two concurrent heads when both supersede a formerly shared head. That is useful for knowledge/history merging, but **it is not a branch compare-and-swap rule**. Gitr must still reject a stale expected ref when its protocol requires that behavior. [crates/mnem-backend-redb/src/op_heads.rs](https://github.com/Uranid/mnem/blob/2a8a36985dbcf107378a76daeeef7154691220e7/crates/mnem-backend-redb/src/op_heads.rs); [crates/mnem-core/src/store/op_heads.rs](https://github.com/Uranid/mnem/blob/2a8a36985dbcf107378a76daeeef7154691220e7/crates/mnem-core/src/store/op_heads.rs); [crates/mnem-backend-redb/Cargo.toml](https://github.com/Uranid/mnem/blob/2a8a36985dbcf107378a76daeeef7154691220e7/crates/mnem-backend-redb/Cargo.toml).

**yuchenZhangTG/graft** contains a CAS, chunking, lease/ref/merge service modules, virtual workspaces and Git import/export paths. Its inspected ref handler delegates conditional updates to a `MetadataStore`. This is a useful design and implementation candidate, but its manifest bundles SQLite and includes ring and optional FUSE. Adopting that application wholesale would import a different persistence and native dependency design. Evaluate the chunking, metadata interface and workspace logic separately. [src/daemon/ref_service.rs](https://github.com/yuchenZhangTG/graft/blob/91d9a891276c939e2ea8d8e662fa6785c26c99e9/src/daemon/ref_service.rs); [Cargo.toml](https://github.com/yuchenZhangTG/graft/blob/91d9a891276c939e2ea8d8e662fa6785c26c99e9/Cargo.toml).

**Naridon-Inc/aura** has an isolated `aura-attestation` crate for canonicalized signed blocks, actor identity and chain verification. It is a plausible provenance donor. The reviewed crate explicitly supports Ed25519 only and defers additional algorithms, so it does not provide gitr's PQC policy without further work. [crates/aura-attestation/src/lib.rs](https://github.com/Naridon-Inc/aura/blob/e356f08f22560258bf439dca24fe5dfa31d6f080/crates/aura-attestation/src/lib.rs).

## Components worth importing as units

1. **Graph layout:** ferrislabs/gitr `crates/graph`, its domain types, and layout tests. Keep input-topology requirements explicit.
2. **Wire and pack codecs:** evaluate git-zero core/client/server modules behind gitr-owned I/O and stable database snapshots.
3. **Async object algorithms:** evaluate girt `ObjectRead`/`ObjectWrite`, selected pack and object algorithms, and its verified-result constructors. Do not inherit filesystem ref durability assumptions.
4. **Interoperability fixtures:** adapt cNameHitch/gitr and smaller MIT/Apache projects' format cases. Pin C Git behavior and require strict errors/state comparison rather than copying a passing-test count.
5. **Fuzzing:** import the actual mayhemheroes/git-rs libFuzzer target pattern without requiring the hosted Mayhem service.
6. **API/agent schemas:** adapt ekhodzitsky/gitr command types and parser examples; route operations through gitr's authenticated authority.
7. **Forge events:** evaluate grite issue/event types and projections while retaining one gitr persistence model.
8. **Optional knowledge/indexing:** evaluate mnem redb modules as derived search/history components. They do not replace Git object identity or branch-CAS semantics.
9. **Provenance:** evaluate aura's canonicalization/attestation modules with an explicitly chosen signature suite.
10. **Virtual workspaces:** evaluate graft's small interfaces and chunking/lease implementation after checking behavior against gitr's concurrency and recovery requirements.

## Adoption gates specific to these findings

- Pin an exact upstream commit and preserve license/notice provenance for every imported component. GitHub metadata alone is insufficient when LICENSE text or manifest disagrees.
- Separate Git object identity and wire compatibility from internal storage IDs and metadata schemas.
- Require DB snapshot consistency for object enumeration while serving fetch, and durable object/ref publication before receive-pack success.
- Test cancellation, graph/object-count limits, malformed delta chains, thin packs, SHA-1/SHA-256 handling, stale ref expectations, and restart during publish. These risks follow from the actual donor boundaries above.
- Measure complete dependency closure, including `git2`, compression providers, TLS crypto, SQLite, Tree-sitter and subprocesses, before calling a selected build all Rust.
- Record which behavior came from upstream evidence and which was reproduced in gitr. This research did not claim independent test passes, speedups, complete Git parity, or production readiness.
