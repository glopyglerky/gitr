# Established VCS engines, Scion implementations, and component reuse

Survey date: 2026-11-08, America/Denver. Gitr was inspected at `69a16ea1506d8efa20dff0e559b5716dc95743bd` on `master`. This appendix complements the name-family, forge/CI, and storage/search reports. Its machine-readable evidence is in [core-vcs.json](core-vcs.json) and [core-search-ledger.json](core-search-ledger.json).

## Recommendations

Keep Gitoxide as the current engine while evaluating small, well-defined additions. Its existing object, index, worktree, and reference integration has value that a new similarly named project does not automatically replace. Use the girt and git-zero candidates from the [name survey](name-search.md) to close specific transfer or storage-interface gaps. Give each candidate the same strict Git compatibility and crash-recovery tests before changing the engine.

The most useful additional component-level findings in this pass are Josh's current gix-based helpers and repository projections, Sapling's separately MIT-licensed DAG library, Jujutsu's operation-store contracts, and the public Scion implementations' typed storage and durability tests. Their licenses and architecture differ. The user's authorization to choose a suitable license for Gitr's own work allows Apache-only candidates to remain under consideration; it does not erase licenses on inherited Git or other donors.

## Meta's systems: isolate the libraries with a usable contract

[Sapling](https://github.com/meta/sapling/tree/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb) is a collection of client, server, filesystem and supporting libraries. Its root license does not describe every component. `eden/scm/lib/dag` declares **MIT** in its [manifest](https://github.com/meta/sapling/blob/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb/eden/scm/lib/dag/Cargo.toml) and carries its own [MIT license](https://github.com/meta/sapling/blob/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb/eden/scm/lib/dag/LICENSE). The [library entry point](https://github.com/meta/sapling/blob/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb/eden/scm/lib/dag/src/lib.rs) exposes DAG traversal, ID mapping, segments, sets and ancestry-related algorithms.

That library is a plausible whole-library evaluation target for commit-graph acceleration. Follow all local path dependencies and their licenses before extraction. Keep Git OIDs as the durable external identity; internal dense graph IDs are indexes. Do not substitute semantic vectors for these exact relationships.

Mononoke's [architecture](https://github.com/meta/sapling/blob/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb/eden/mononoke/docs/1.3-architecture-overview.md) is useful for separating immutable blobs, repository metadata, derived data and request services. Its [public README](https://github.com/meta/sapling/blob/f7a6003b0bbc083ddef7a40f34f0b13f3f420fcb/eden/mononoke/README.md) says the open build supports MySQL, SQLite, file and S3 backends but omits functions, including MySQL failover support and some internal APIs/configuration documentation. It does not supply Gitr with an independently qualified, redb-backed HA forge merely by being available as Rust source. Sapling/EdenFS also include non-Rust code. Whole-system adoption would violate the lightweight standalone objective.

## Binary assets and data-oriented alternatives

The existing [asset catalog](../../upstreams.md) already explains Git LFS compatibility. The following checks refresh its core selection without changing Gitr's format contracts.

- [EpicGames/lore](https://github.com/EpicGames/lore/tree/c1ba69decf991b4aadb84dd3fb32971fe2859160), MIT, remains a strong storage-component donor. Its [workspace](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/Cargo.toml) separates `lore-io`, `lore-storage`, revision, transport and server libraries. [lore-storage's manifest](https://github.com/EpicGames/lore/blob/c1ba69decf991b4aadb84dd3fb32971fe2859160/lore-storage/Cargo.toml) depends on `zstd-sys`. Borrow fragment/range/cache mechanisms without replacing Git history or ordinary LFS SHA-256 pointers.
- [Hugging Face xet-core](https://github.com/huggingface/xet-core/tree/5385084c6e15f0cedd2ca8a2e36279413b049e0c), Apache-2.0, supplies chunked CAS-transfer reference code. Its [git-xet adapter](https://github.com/huggingface/xet-core/blob/5385084c6e15f0cedd2ca8a2e36279413b049e0c/git_xet/README.md) is negotiated through Git LFS and requires the relevant server. It does not make GitHub's ordinary LFS endpoint accept a different protocol.
- [Oxen](https://github.com/Oxen-AI/Oxen/tree/0d3045335f93d77171f95f599a3cee3a080622ae), Apache-2.0 metadata, is relevant for large datasets and data-aware changes. Its [workspace](https://github.com/Oxen-AI/Oxen/blob/0d3045335f93d77171f95f599a3cee3a080622ae/Cargo.toml) uses RocksDB with bindgen and native compression. Its [product model](https://github.com/Oxen-AI/Oxen/blob/0d3045335f93d77171f95f599a3cee3a080622ae/README.md) is not a promise of Git's exact repository/wire formats. Evaluate application behavior and selected data-diff components, not its whole engine as a replacement for redb.
- The [storage/search appendix](storage-search.md) covers the more immediately relevant modular Rust LFS client, Rudolfs, LFSX and Iroh helpers, including native-process and license boundaries.

## Pijul and non-Git histories

[Pijul's official site](https://pijul.org/) points to the [Nest repository](https://nest.pijul.com/pijul/pijul), not the old `pijul-scm/pijul` GitHub repository, whose metadata reports a 2017 push. The current Nest listing includes `pijul-core`, `pijul-repository`, `pijul-remote` and `palimpsest`. The web tool could read the listing but not the current file bodies; raw file reads failed because the tool rejected octet-stream content.

The version-specific published [libpijul 1.0.0-beta.11 manifest](https://docs.rs/crate/libpijul/1.0.0-beta.11/source/Cargo.toml.orig) declares GPL-2.0-or-later and default on-disk features that include zstd. Pijul's [official license FAQ](https://pijul.org/faq) also states GPL2 or later. These statements do not establish a complete current dependency/license audit of the reorganized Nest tree.

Pijul is a useful change/merge model reference. Replacing Git commits with its patch identity would change the product's compatibility contract. Reuse any algorithm only with a demonstrated mapping to Git behavior and an appropriate component license. Do not call importing Git history a two-way Git protocol implementation.

## Inspection limits

This is a source and interface survey. It read 51 successful pinned source/manifest/document paths for this appendix, plus repository metadata, trees, official pages and fork comparisons. It did not execute upstream test suites, import code, establish benchmark results, prove cryptographic quality, or audit every function. Metadata-only rows remain a backlog. The acceptance gates in the main survey describe the concrete tests required for adoption.
